# The Vulkan renderer

The renderer's backend for Vulkan, behind the renderer's command stream
(`xgpu_stream_*`), as Metal's is on macOS (`port/macos/xgpu_metal*.m`): the
guest records each frame as a stream, and the host replays it with Vulkan.
It is the renderer of the Linux builds, `ninja linux_x86_64` and `ninja
linux_arm64` (the guest on the host, `tools/linux_guest_build.py`), whose
guest has the computer's architecture: `x32` on x86-64, `arm64_32` on ARM;
of the Windows build (`ninja windows`) and of the Android app (`ninja
android`). Each host builds the Xbox's texture decoding for it
(`tools/vulkan_build.py`).

| File | What it is |
| --- | --- |
| `port/linux/src/xgpu_spirv.c` | The shaders: the NV2A's programs (the shader IR, `xgpu_shader.h`) written as SPIR-V |
| `xgpu_vulkan.c` | The device, memory, images, samplers, pipelines, passes, draws, visibility queries, the swapchain |
| `xgpu_vulkan_stream.c` | The stream's backend table: each record made into the calls above |
| `xgpu_vulkan_textures.c` | Textures, decoded by the shared Xbox decoder (swizzled, palettes, 3D) where Vulkan cannot sample them as they are (DXT as ASTC 4x4 instead on the Android app's devices without BC: `display.astc_textures`, `port/linux/astc`), and the VR mode's effects' thickness kept with them |
| `xgpu_vulkan_effects.c` | The VR mode's effects' arithmetic on the CPU: an effect bitmap's thickness, each eye's transforms between the world and its pixels (tested alone: `tests/effects_test.c`) |
| `xgpu_vulkan_post.c` | `display.anti_aliasing`'s FXAA and SMAA passes |
| `xgpu_vulkan_post_shaders.c` | Their shaders and SMAA's lookup textures, generated by `tools/vulkan_post_shaders.py` from its GLSL, and the pixel shader of the clears of some colour channels |
| `host_vulkan.c`, `guest_vulkan.c` | The window: SDL's Vulkan surface handed from the guest to the host |
| `host_vulkan_vr.c` | OpenXR eye and composition passes, with the VR stream's late latch (`port/linux/host/host_vr_stream.c`) |
| `xgpu_vulkan_vr_glsl.inc` | The fixed composition passes' GLSL (not compiled) |
| `xgpu_vulkan_vr_shaders.c` | Their SPIR-V, generated by `tools/vulkan_vr_shaders.py` from `xgpu_vulkan_vr_glsl.inc` |

## Build and run

    python3 configure.py
    ninja linux_x86_64          # (ninja linux_arm64 on 64-bit ARM)
    build/linux_x86_64/halo

For OpenXR, add `--vr` to `configure.py`. The runtime must offer
`XR_KHR_vulkan_enable2`.

The OpenXR runtime chooses the Vulkan device and supplies its swapchain
images through `XR_KHR_vulkan_enable2`. The host keeps those 64-bit images;
only image indices cross to the 32-bit guest. Scene rendering uses stereo
multiview, or four views for the existing eye-tracked foveation (periphery
and inset for each eye). The HUD, scope and visor take the game's state,
the late latch and display pacing from the VR stream
(`port/linux/host/host_vr_stream.c`). The final images are copied to the
runtime's acquired images and submitted before release. Runtime fragment
density maps are not used by this path. The instance keeps the extensions
SDL's window surface needs, and the window its surface: if the runtime
refuses the instance or device, they are made again without it, and if VR
cannot start later (no session, no swapchain format), the game plays flat
in the window (`VR unavailable: ...; playing flat` in the log).

A full-target clear at a pass's start uses `loadOp=CLEAR`, so the driver
need not load the old attachment. Partial clears and aspects not cleared
preserve their pixels. By default every pass stores its attachments: later
scope, cockpit and runtime-depth passes can read the depth.
`HALO_VULKAN_STATS` includes attachment loads and clears.

Discards (on by default since they were measured on the Steam Frame,
#335; `HALO_VULKAN_DISCARDS=0`: off) store less from a tiler's tile memory, as the Metal backend
does (#131). Each pass's draws go into a secondary command buffer, and the
pass's `vkCmdBeginRendering` is made at the submission, when what the
later work does with its attachments is known (`xgpu_vulkan.c`, "the main
command buffer in segments"):

- an attachment that a later pass of the submission clears whole before
  anything else uses it is not stored; one that anything later loads,
  samples, copies, resolves, reads back or presents is stored, as before
  (a later piece of the same targets, after the backend split the pass for
  an upload or a copy, loads what the earlier piece stored);
- the frame's last pass does not store a depth/stencil or multisampled
  image whose first use in each of the last 30 frames cleared it whole; any
  other first use starts the count again, and is logged once if the frame
  before discarded it;
- a multisampled target's resolve right after the pass that drew it is made
  in that pass (`resolveMode` AVERAGE for colour, SAMPLE_ZERO for depth and
  stencil), and a resolve of samples not drawn since their last resolve
  into the same, unchanged image is not made again;
- where the device has lazily allocated memory, the multisampled targets
  are transient attachments in it (`HALO_VULKAN_TRANSIENT=0`: not; `=force`:
  transient in ordinary memory, to try the path on a desktop's GPU).

Where the device lacks a part (no SAMPLE_ZERO resolve of depth and stencil,
no lazily allocated memory: a desktop's GPU), that part is as without
discards. `HALO_VULKAN_STATS` counts the stores discarded and the resolves
made in passes, and times each frame on the GPU.

With discards, passes are also put aside (#335, as the Metal backend's
are; `HALO_VULKAN_ASIDE=0`: not). The game draws into other targets in the
middle of its 3D view (the shadows, the motion sensor, the effects'
targets), and each of those passes ended the view's pass, whose next piece
loaded what the one before stored: on a tiler, the view written out of
tile memory and read back each time (`xgpu_vulkan.c`, "aside passes"):

- a pass that draws colour alone, not multisampled, into other targets
  than the pass recorded before it, and the copies and image uploads about
  it, are played before that pass;
- the next pass of the interrupted pass's targets, area, layer and views,
  which loads every attachment and stores as it, continues it: the pieces
  are one rendering (each piece's secondary command buffer executed in it),
  with the first's loads and the last's stores and resolves.

The order changes only where neither side reads what the other writes:
what is put aside may not sample, copy or resolve the interrupted pass's
targets, nor write an image one of its pieces sampled; that, a pass with
depth or multisampled, or other work outside passes (a buffer written in
order, a readback, the lights' upload, the present) keeps the order drawn
from there. A mirror's buffer that the submission reads, written again, is
renamed instead of written in the frame's order (which ends the pass): a
spare buffer of its size takes its place, its bytes copied from the old
one by the submission's early commands, and the draws recorded before keep
reading the old one. `HALO_VULKAN_STATS` counts the passes continued, those
put aside and the buffers renamed.

A clear of some of the colour's channels (the game's clear alpha alone: a
fog screen's, with or without depth, and each window's end in a split
screen) is drawn, as `vkCmdClearAttachments` cannot clear through a write
mask: one triangle over each of the clear's
rectangles (the anti-aliasing passes' vertex shader, and a pixel shader that
writes the uniforms' colour, `tools/vulkan_post_shaders.py`), through a
pipeline whose write mask is those channels, with no depth or stencil test
or write, of the targets' formats, samples and views (every view of a
multiview pass, every sample of a multisampled target). Depth and stencil
are cleared as before, a whole attachment's as its pass begins, so a fog
screen's whole-target clear keeps that fast path for its depth; a clear of
every channel is never drawn. The triangles count no samples of a visibility
test. Their pipelines are made as a map is prepared: the clear of alpha for
each of the targets the map's draws go to, and any other the enumeration's
clears ask for; `HALO_VULKAN_STATS` counts the clears drawn.

`display.prepare_shaders` uses the shared per-map enumeration before play.
Fixed VR composition pipelines are made at VR initialization. A new scene
pipeline after preparation logs `pipeline missed map preparation`, with the
variant that needs coverage.

Configuring once fetches the Khronos Vulkan headers (a pinned release, checked
by SHA-256) into `build/<build>/third_party` (`build/linux_x86_64/third_party`,
`build/linux_arm64/third_party`, `build/android/third_party`); the game loads the system's
`libvulkan.so.1` when it starts. It needs Vulkan 1.3 (dynamic rendering,
timeline semaphores, host query reset), precise occlusion queries, and a
combined depth/stencil format that supports both attachments and sampling
(D32S8, or D24S8: depth is kept reversed, 1 - the game's, which a float holds
finely at a distance, in the VR build's eyes as in the window, and in the
depth the VR build gives the headset's compositor; `xgpu_backend.h`,
"Reversed depth"). Its driver must expose these features. VR also requires
stereo multiview and depth clamping for the sky; four-view foveation requires
four multiview views and fragment storage-buffer atomics.

The game's settings for finding problems in the graphics (`port/linux/README.md`)
reach the host with the window (`host_vulkan_window_open`: the host does not
read the settings file): `debug.gpu_validation` (and its deprecated old
name, `debug.gl_debug`), `debug.gpu_stats` and `debug.gpu_dump_shaders` do
what the variables above do; `debug.texture_dump_directory` writes each 2D
texture's first level as it is read, decoded to BGRA
(`tex<number>_fmt<format>_<width>x<height>.tga`, 32-bit, rows from the top,
numbered in the order the textures are read; `xgpu_vulkan_textures.c`).
`debug.gpu_debug_expression` (an expression put into each pixel shader,
which the SPIR-V written directly has no place for) is Metal's alone, and
does nothing here.

## The window

`display.vsync` chooses the present mode: FIFO waits for the display;
without it, mailbox (no tearing) where the surface has it, else immediate.
The guest hands the setting to the host with the window
(`host_vulkan_window_open`, called again when it changes), and the
swapchain is made again for it. With battery saver on
(`display.battery_saver`, the guest's `battery_saver.c`), the host shows
each frame for the whole number of the display's refreshes that brings the
frames a second to 30 to 60 (`frame_pacing_divisor`): FIFO shows one image
a refresh, so the frame is presented that many times
(`xgpu_vulkan_frame_end`), and the render thread, and with it the game,
waits for the display. The VR build's headset is presented through OpenXR,
where none of this applies.

With FIFO, `display.low_latency` (`xgpu_vulkan_pacing.c`; "Low latency
with vsync" in `port/linux/README.md`) paces the game by the display: the
device is made with `VK_KHR_present_id` and `VK_KHR_present_wait`, and
`VK_GOOGLE_display_timing`, where it has them; each present gets a number
(`VkPresentIdKHR`, `VkPresentTimesInfoGOOGLE`), and a thread of its own
waits for the frame's work (the timeline) and then for its present, in
order, and tells the command stream (`host_render_stream_frame_displayed`)
when the display took it and when it was shown. The game then starts a
frame only while one at most waits for the display, its budget before the
refresh it is for, and the swapchain has three images (the least the
surface allows, if more). A swapchain made again lets go of its presents
first: those not yet shown count as shown, and the thread no longer waits
for them. A frame that presents nothing (the window hidden, the app in the
background, a held frame) is taken at once.

The surface is made again when the driver reports it lost
(`VK_ERROR_SURFACE_LOST_KHR`, from the acquire, the present or the
surface's capabilities), on every build. On Android it is also let go of
as the app goes to the background and made again as it comes back
(suspend and resume): Android takes the app's window away when the app
stops and gives it a new one when it returns, and SDL makes again only
EGL's surfaces. On SDL's `WILL_ENTER_BACKGROUND` and
`DID_ENTER_BACKGROUND`, the render thread waits for the GPU, lets go of the
swapchain and the surface, and saves the pipeline cache; frames drawn in
the background are submitted but not presented, so nothing waits for a
display. On `DID_ENTER_FOREGROUND` the surface is made again with
`SDL_Vulkan_CreateSurface`, or at a later frame while the window is not
back yet (Android resumes the app before it makes the window's surface).

A phone held sideways reports its surface turned (`currentTransform`).
The swapchain is then made for the display's own orientation (its width and
height swapped for a quarter turn, `preTransform` the surface's), and the
frame is drawn turned into an image of its own (`xgpu_vulkan_post_rotate`,
a draw: a blit cannot turn) before the present blit, so that the compositor
has nothing to turn and no `VK_SUBOPTIMAL_KHR` to report. A
`VK_SUBOPTIMAL_KHR` present makes the swapchain again only if the surface's
extent or transform changed, and asks the surface at most once a second.

The pipeline cache is written (atomically: a temporary file renamed over
it) when pipelines were made since it was last written: at exit, after a
map's preparation, and as an Android app goes to the background, since
Android seldom lets an app exit cleanly.

A window SDL cannot draw with Vulkan (its offscreen driver: NVIDIA's driver
has no headless surfaces) is drawn without a swapchain: the frames are drawn
and read back for screenshots, but not shown.

## Shaders: SPIR-V written directly

`xgpu_spirv.c` writes SPIR-V 1.3 (Vulkan 1.1) from the shader IR, as
`xgpu_msl.c` writes Metal's language from it. The alternative, GLSL for Vulkan
compiled by glslang, would put a GLSL compiler in the game (megabytes, and
milliseconds a shader): the shaders are made while the game draws, from
pipeline keys, not ahead of time, so they cannot be compiled when the game is
built. Written directly, a module takes microseconds and needs no library.

The layout: set 0 has the vertex program's constants (binding 0, a dynamic
uniform buffer), the shaders' other uniforms (1, dynamic), the dynamic lights
(2), their grid of cells (3) and the sample counters (4); set 1 has the four
textures (bindings 0 to 3). The vertex shader negates y (the NV2A's screen is
y down, as Vulkan's framebuffer is, and the clip space is OpenGL's) and its
position is `Invariant`, with the arithmetic it depends on `NoContraction`.

`tools/spirv_corpus` writes the Metal corpus's variants as SPIR-V and checks
each with `spirv-val` (its README).

## As OpenCE's OpenGL backend drew

The aim was the pixels of OpenCE's OpenGL backend, which this one replaced.
What was measured on an RTX 4090
(NVIDIA's driver, both APIs), drawing the same triangles both ways:
rasterization, interpolation, filtering, BC1 to BC3 decoding and short vertex
attributes are identical. Where the drivers differ, the backend makes up the
difference on NVIDIA's proprietary driver alone:

- Anisotropic filtering: NVIDIA's OpenGL centres its blend between mip levels
  where its Vulkan begins it at the lower level; a LOD bias (-42/256 at 2x
  and 3x, -54/256 at 4x to 7x, -64/256 at 8x to 16x) makes them identical.
- Cube maps: the OpenGL backend left seamless filtering off, so cube maps
  are sampled without it (`VK_EXT_non_seamless_cube_map`), where the device
  has it.

NVIDIA's OpenGL compiler fuses multiplications into the additions that use
them; its Vulkan compiler fuses none. Fusing them in the SPIR-V as OpenGL's
compiler does (explicit `Fma`) changed no pixel of Blood Gulch, so it is not
done: the remaining differences (a few thousand pixels a frame, most by one
level) are rounding in the shaders.

## The enhanced dynamic lights

The front end's lights block and grid of cells (`xgpu.h`) are the draw set's
uniform buffer and `R32G32B32A32_UINT` 3D image, written in the stream's
order: before the submission's draws (no pass ended for them), unless a draw
recorded in it read the lights, then after it. The lit structure and models
are the SPIR-V emitter's (the lights, their sum and shoulder, as
structured loops). The glows are a pass after the transparent geometry: a
quad about each bolt's light, its vertices in the upload ring, projected with
the eyes' and the foveated insets' corrections as the game's vertex shaders
are, into every layer of the target in one multiview pass, without the depth
attachment, which the pixel shader samples (resolved, where it is
multisampled) to fade the glow. Their pipeline is prepared with the map's
enumeration; `HALO_VULKAN_SHADERS` writes their modules as `halo_*.spv`
(the VR mode's eyes': `glow_*.spv`, below).

## The VR mode's effects

In the VR mode's eyes the game's effects, drawn with its effect shaders
(particles, contrails, weather), are drawn with depth, always, and the
glows of the enhanced dynamic lights as their bolts' light. The flat screen
draws them as before. As drawn:

- The game marks each effect's draws (the pixel key's `vr_effect`,
  `halo_vr_effect_depth` in `d3d8_device.c`): soft, or soft and thick where
  its build's largest sprite is at least 2 degrees wide on the screen
  (`render_sprite.c`); not the first-person weapon's, nor one drawn
  without depth. A z-sprite (a bullet impact's puff: its pixel shader's
  DOT_ZW stage computes the depth of a rounded puff up to the sprite's
  radius nearer than its card) is soft, not thick, and its fade is measured
  from the puff's own depth (no farther than the card), not the card's
  (`effect_zsprite_fade`). That fade is its depth test: its pipeline tests
  and writes no depth (the floor would cut the card in half), and a pixel
  whose puff is behind the scene is discarded, so no shader writes depth on
  the Adreno (which can turn off its hierarchical depth for the rest of the
  pass). Flat, and outside the effects, a z-sprite's shader writes that
  depth instead (conservatively: SPIR-V's `DepthLess`, MSL's
  `[[depth(less)]]`). Sprites facing the
  viewer face the head's centre and stay upright in the world; the game
  draws the 3D view once, from the head's centre, so both eyes see the same
  card.
- Its pixel shader (`xgpu_spirv.c`, `effect_prelude`) finds the world point
  each pixel draws and the scene's behind it, from the depth buffer and each
  view's unprojection (the eye's correction, the screen conversion, the
  inset, the viewport: `xgpu_vulkan_effects.c`, in the uniforms), and their
  distances along the eye's ray. It fades the effect toward its blend's
  nothing (alpha to 0, an added colour to black, a multiplied one to white)
  as the two meet, over half the sprite's radius in the world (the radius in
  texels times the texels' size there, from the world's and the texels'
  derivatives), at least 0.02 world units (6 cm), and a 500th of its
  distance (more than the depth buffer's steps there).
- Each effect bitmap's thickness is baked as the map loads (its
  enumeration draws every effect's every bitmap, thick: the texture cache
  bakes a bitmap's the first time a thick draw has it, from its first
  level; `xgpu_vulkan_effects.h`): each sprite's texels' distance to its
  silhouette (exact Euclidean, over its connected texels), a sphere's
  profile of it (a disc becomes a hemisphere), smoothed, scaled by the
  square root of its alpha, with the sprite's radius beside it, an RGBA8
  image kept with the texture (`HALO_VULKAN_STATS` logs those baked and the
  time). A texture with one is kept though not drawn for the half minute
  after which the cache lets others go, until the guest writes its texels
  (the next map), so play does not bake them again.
- Thick, the sprite is a bulge toward the eyes half its radius high at its
  middle (`XGPU_SPIRV_EFFECT_THICKNESS`: a sphere's depth made smoke look
  like balloons). Each eye's ray meets the bulge's front a little to one
  side of where it meets the card, and texture 0 is sampled there: one
  parallax step, which is exact enough for a smooth bulge seen near its
  normal (the eyes' rays are within a degree or two of it), where a march
  would sample the bitmap several times. The two eyes sample different
  texels, so the effect has depth inside it. The fade is measured from the
  bulge's front over its thickness, so an effect meets a wall along its
  shape, not its card's plane. The depth is not written (a pixel shader
  that writes it turns off early depth testing, and the effects write none).
- The depth is sampled in a pass that writes none of it (`reads_depth`):
  the first effect of the frame ends the pass the scene was drawn in (whose
  depth is stored), and the effects and whatever else writes no depth or
  stencil draw in the next, which stores neither (`VK_ATTACHMENT_STORE_OP_NONE`).
  A draw that writes depth or stencil ends it again. The glows are drawn in
  it too (the depth bound, untested), so they need no pass of their own.
- The glows (`display.dynamic_lights = "enhanced"`) are the light each bolt
  scatters toward each eye from a haze about it, whose density falls off
  as the card's glow did across it (a wide Gaussian less its value at the
  edge, and a narrow core): along each eye's ray the integral is closed, an
  error function's difference for each Gaussian (Abramowitz and Stegun's
  7.1.27), from the eye to the scene's surface behind the pixel. Unhidden,
  it is the card's glow exactly; a wall through it hides what is behind it.
  The quad drawn covers the haze's outline from the head (or the view, with
  the head inside it).

What they cost, estimated (not yet measured on a Steam Frame: its
`HALO_VR_GPU_TIME=1` and `tools/gpu_busy.py` say): an effect pixel's shader
is some 30 SPIR-V operations (texture 0 times the vertex colour), soft about
100 (two more texture reads: the depth, the thickness), thick about 160; a
glow pixel's 35 as a card, 130 as scattered light. On the Frame's Adreno 750
that is some 0.07 ms a million soft effect pixels, 0.13 ms thick: a fight's
few million effect pixels a frame (both eyes, overdraw included) about
0.2 to 0.4 ms, a grenade's smoke filling the view a moment's 2 ms. The pass
the depth is read in costs nothing more where the frame has glows (their
pass was one already); otherwise, on a tiled GPU drawing in its tile memory,
one more store and load of the eyes' colour and a load of their depth, up to
about 1 ms at 1728 x 1728 (less foveated), nothing drawing in system memory.
The bake is the map's loading's, a millisecond or so a bitmap.

## Anti-aliasing

`display.anti_aliasing = "fxaa"` and `"smaa"` are passes over each
window's 3D view after the lens flares, before the HUD and the menus, so
that their text stays sharp. Their GLSL, FXAA's and SMAA's (at its HIGH
preset, `port/third_party/smaa`), is `tools/vulkan_post_shaders.py`'s
(`VERTEX_SOURCE`, `FXAA_SOURCE`, `SMAA_MAINS`), compiled to SPIR-V by it
(with glslang, run by hand when the passes change: the game has no shader
compiler), which checks each module with `spirv-val` and writes
`xgpu_vulkan_post_shaders.c` with SMAA's lookup textures inflated. Only the
interface changes: the uniforms are a block (set 0, binding 1), the
samplers' texture units their bindings (set 1). After changing the GLSL,
run the tool again (`--check` says whether the file matches), and
`tools/metal_post_shaders.py`, which makes Metal's from the same GLSL.

The target's rectangle is copied first, so that no pass reads
what it writes; each pass draws one triangle over the rectangle, in a pass
of its own (the barrier at its end is what the next samples after); SMAA's
edges and weights are cleared whole as their passes begin; only colour is
written back into the target (the game keeps values of its own in its
alpha). The intermediate images are the target's size; SMAA's lookup
textures are RGBA8 images of its RG8 and R8 (the rest zero). The pipelines
are made when the setting is chosen, and requested with the map's
preparation. Android draws SMAA too. The VR mode's eyes have neither pass: the game
antialiases only the flat screen's 3D view (`source/render/render.c`).

## Ambient occlusion

`display.ambient_occlusion` (`"off"`, `"subtle"`, `"strong"`: Enhanced's)
shades each window's 3D view once its opaque surfaces have drawn their
light, only where the game's lighting does not hold the occlusion: the game
calls `halo_screen_ambient_occlusion` after the structure's lightmap pass
(`source/render/render.c`), before the diffuse textures, the decals, the
dynamic lights, the specular light, the transparent surfaces and the
effects. As they draw, objects (models) mark their pixels in the stencil's
bit 6 and self-illuminated surfaces in bit 7 (`pipeline_state_describe`);
the first-person weapon's is the game's bit 0. The record
(`XGPU_STREAM_AMBIENT_OCCLUSION`) carries the camera, and the passes
(`xgpu_vulkan_post.c`, their GLSL in `tools/vulkan_post_shaders.py`) are:

- the depth target (its first sample's, resolved where it has more) made
  the distances along the view, each a half float and what it leaves;
- the mask: the stencil's bits made a texture by draws tested against them
  (red an object's pixel, green one left as it is);
- GTAO (XeGTAO's horizon integral) at half the resolution: in two
  directions a pixel, turned by a 4x4 Bayer matrix, the highest horizon
  each side within 0.5 world units, its normal from the depth. An object's
  pixel (one ambient sample lights it) counts every sample; the level's
  (its radiosity lightmap holds its own occlusion) only objects', so that
  no corner is darkened twice;
- a blur along x and then y, nine taps weighted by their distances'
  nearness, none across an object's edge;
- a draw over the target multiplying its colour (not its alpha), filtered
  up by the nearest four weighted by their distances, none over the pixels
  the mask leaves.

The target's pass ends for them and begins again, loading what it drew.
`debug.ambient_occlusion_view` draws the occlusion alone in the view's place
before the HUD. Metal draws the same passes (`port/macos/xgpu_metal_post.c`,
their MSL written from this GLSL by `tools/metal_post_shaders.py`), but not
over a multisampled target.

## HDR

`display.hdr` is the shared contract of [docs/hdr.md](../../../docs/hdr.md);
this is the Vulkan half, on the Linux desktop (not Android, not the VR
mode). The renderer says it draws HDR where the device reads a colour
attachment where it is drawn (`VK_KHR_dynamic_rendering_local_read`, with
sample shading and half floats it blends into): the front end's back buffer
is then RGBA16F, an input attachment too.

- A draw whose tag blends in its shader (a ceiling, a glow, the alpha
  limit) has its pipeline's blending off; its SPIR-V (`xgpu_spirv.c`,
  `hdr_output`, the MSL emitter's operation for operation) reads the pixel
  it draws over as input attachment 0 of a third descriptor set, each
  sample's own of a multisampled target. The core binds the attachment as
  that input and orders the draw after the pass's draws before it with a
  framebuffer-local barrier (by region), or, where the device orders
  attachment reads in rasterization order
  (`VK_EXT_rasterization_order_attachment_access`), with none, its own
  overlapping triangles in order too. Without that extension, two
  triangles of one tagged draw over the same pixel read it unordered (the
  tagged draws are surfaces, HUD bitmaps and glows, which seldom overlap
  themselves).
- The tone map is the shared GLSL (`xgpu_hdr.c`) compiled to SPIR-V by
  `tools/vulkan_post_shaders.py` (the same source `tools/metal_post_shaders.py`
  makes Metal's from), drawn as a triangle in the pass that drew the view,
  reading each pixel where it is drawn, as Metal's reads tile memory: no
  pass of its own, no copy. Anti-aliasing then runs on the half floats.
- The swapchain is HDR while the frames are HDR and the window's display
  shows HDR (SDL's `SDL_PROP_WINDOW_HDR_ENABLED_BOOLEAN`, read at the start
  and on `SDL_EVENT_WINDOW_HDR_STATE_CHANGED`) and the surface has an HDR
  colour space (`VK_EXT_swapchain_colorspace`): HDR10 (A2B10G10R10, PQ,
  BT.2020's primaries), Linux compositors' own, or scRGB (half floats,
  extended linear sRGB); `HALO_VULKAN_HDR_OUTPUT` (`"pq"`, `"scrgb"`)
  chooses where it has both. The frame is encoded for it
  (`xgpu_vulkan_post_encode`: linear, at most the display's peak, times
  paper white) into an image of its own, letterboxed into the swapchain as
  an SDR frame is, and `VK_EXT_hdr_metadata` gives the compositor the
  content's gamut (sRGB's) and light (the display's peak) where the device
  has it. Paper white is `display.hdr_paper_white_nits`, or with it 0
  SDL's SDR white (or BT.2408's 203 nits where the system says none) times
  `display.hdr_paper_white`'s percent, at most the peak; the peak is SDL's
  headroom over its SDR white. `HALO_VULKAN_HDR_HEADROOM` stands in for SDL's (HDR on, that
  headroom). The front end's `"auto"` follows what the renderer tells it
  (`host_render_stream_display_hdr`): the display shows HDR and the surface
  can.
- On Linux only a Wayland window has an HDR state: SDL reads its display's
  headroom from the compositor's colour management (`wp_color_manager_v1`:
  the surface's preferred peak over its reference white; KDE Plasma 6,
  GNOME 48 and later), and the driver gives the surface its HDR colour
  spaces through the same protocol (NVIDIA's recent drivers, Mesa's). The
  compositor shows the encoding's reference white (PQ's 203 nits, scRGB's
  1.0) at its own SDR brightness, so the frame is encoded relative to it;
  the SDR brightness's nits (for the log, and a paper white set in nits)
  are the patched SDL's `openh1.wayland.reference_luminance`
  ([docs/hdr.md](../../../docs/hdr.md)). The
  game is a Wayland window wherever SDL prefers one: in a Wayland session
  whose compositor has `wp_fifo_manager_v1` (KDE 6.4 and later, Hyprland;
  `SDL_VIDEO_DRIVER=wayland` or `x11` chooses). Under X11, XWayland and
  gamescope (whose games are X11 windows) SDL says nothing of HDR, so the
  game is SDR even where gamescope's layer gives the surface HDR colour
  spaces, unless `HALO_VULKAN_HDR_HEADROOM` gives a headroom. The log says
  which window system the window is in (`vulkan: the window is SDL's
  wayland`) and what each side said (`vulkan: the display shows HDR
  (headroom ..., a peak of ... nits; swapchain outputs: ...)`, or which
  of them said no).
- With HDR off, and with `"auto"` where the display shows none, nothing
  changes: the back buffer is BGRA8, no pipeline reads its attachment, and
  the swapchain is the 8-bit sRGB one.
- A shot or the determinism log reads the half floats back as an SDR
  display shows them (clamped to 1, 8 bits).

The tests (no Vulkan device needed): `port/linux/vulkan/tests/passes_test.c`
(the barriers and input sets, the pipelines' blending, the swapchain's
choice and the encoding, the tone map's draw), `tools/spirv_corpus` (every
tag over each blend, one sample and four, valid for Vulkan 1.1), and on a
Mac `tools/test_hdr_backends.py`, which makes the Vulkan shaders Metal's
with SPIRV-Cross and runs them on the GPU: the tone map and encoding
against the reference's golden colours, and each tagged draw against the
Metal backend's own over the same pixels.
